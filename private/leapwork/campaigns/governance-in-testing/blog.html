Governance in testing

How to prove every software change was tested and approved

Auditors sample changes and expect a test record and sign-off for each one. Here's what a test automation audit trail needs, and how to build one.

L
[Author name]
November 2026 · 6 min read

When auditors review a regulated system, they rarely look at everything. They sample. They pick a handful of changes and ask two questions about each one: where is the test, and who approved it?

For many teams, answering those questions means a scramble. Someone digs through test scripts, exports results, collects screenshots and pieces together a story that the change was tested before it shipped. SAP teams can spend weeks gathering screenshots for SOX. Validation teams in life sciences run and document GxP tests by hand.

Test automation was supposed to fix this. But most test automation doesn't produce audit evidence on its own. Here is why, and what it takes to close the gap.

Why a passing test isn't proof

A green test run tells you the software behaved as expected at that moment. It doesn't tell an auditor three things they care about:

  • Was the test itself reviewed? If anyone can edit a script and run it, a passing result says little about whether the test checked the right thing.
  • Which version of the test ran? Tests change over time. Without version history, you can't show what was actually checked for a given release.
  • Can you show the run? Logs scattered across tools, or no recording at all, mean evidence has to be rebuilt after the fact.

There's a newer problem too. If AI writes your tests and also decides what happens while they run, the same test can behave differently from one run to the next. That makes results harder to trust, and harder to defend.

What a test automation audit trail needs

A test automation audit trail auditors can follow has four parts.

1

Review and approval before a test is used

Treat tests like any other controlled artifact. A test should move from draft to review to published, and only people with the right role should be able to publish it. In Leapwork, tests move through exactly that flow, and only authorized roles can publish.

2

A version history for every test change

Every change to a test should be logged: what changed, who changed it and when. When an auditor asks what was tested for a specific release, you can point to the exact version that ran.

3

Evidence captured on every run

The fastest way to stop collecting screenshots is to never need them. Every Leapwork run keeps the test version, logs and a video, and results can be exported via API into the reporting or quality tools you already use.

4

Tests that run the same way every time

In Leapwork, AI helps write tests from requirements and links each test back to its source. Then the tests run as fixed steps, with no AI at runtime. You get the speed of AI-assisted authoring and results that behave the same every time.
